A stripped binary, mapped

unwind-map is my biggest project so far. It recovers every function in a stripped Linux binary from the .eh_frame unwind tables that strip can’t remove, then draws them in address order along a Hilbert curve. This is a real run on a 406 KiB program.

About me

I’m teaching myself systems programming and reverse engineering on Windows and Linux. I learn best by building things, so most of what I make is a small tool that shows me one step between source code and a running program: how compilers lay out objects, how linkers put a binary together, how loaders map it into memory, and how debuggers and unwinders read it back.

What hooked me is how much a compiler has to leave behind. RTTI, vtables, unwind tables and import tables all survive stripping, and together they say a surprising amount about how a program was put together. Most of my tools read one of them.

I keep each tool to one job, and the binary-analysis ones have no third-party dependencies, so I can understand every line. I test them on binaries I’ve built myself and compare the results with readelf and llvm-readobj, so I find out when I’ve got something wrong. Each README explains the file format its tool reads, which is how I check I really understand it.

I write C++ for the Windows tools, Rust for the cross-platform command-line ones, C for the low-level parts and Python for scripts, and I’m still learning all four. Along the way I read binaries in Ghidra, GDB, x64dbg and WinDbg.
